# Agent Instructions

This file guides AI coding agents (and future contributors) working in this repository.

## What this project is

A single-page, client-side data center/network topology designer ("DCIM Architect"). There is no backend, no build step, no package manager, and no automated test suite. The entire application — markup, styles, and logic — lives in **`index.html`**.

- Styling: [Tailwind CSS](https://tailwindcss.com/) loaded via the Play CDN (`<script src="https://cdn.tailwindcss.com">`), plus a small `<style>` block for custom scrollbars, selection glow, and animated cable dashes.
- Logic: vanilla JavaScript in one inline `<script>` at the bottom of `<body>`. No frameworks, no modules, no transpilation.
- State: a single global `state` object (`nodes`, `connections`, `zones`, `vlans`, counters, selection, mode, zoom, `highlightVlanId`) plus lookup tables defined near the top of the script: `COMPONENT_METADATA` (device catalog), `CABLE_CONFIGS`, `ZONE_LEVELS` (Purdue levels), `ROLE_TAGS` (server software roles, e.g. Bastion/AD/DNS), and `ACCESS_ROLES` (zone access personas, e.g. DC Manager/CCTV Support — also reused as the persona list for `user`-category nodes' "User Type").
- Zones have a `zoneType`: `'purdue'` (default; styled by `ZONE_LEVELS`) or `'cluster'` (a hypervisor cluster; solid border, styled by `CLUSTER_ZONE_STYLE`). Zones can be drawn nested inside one another — `renderZoneElement()` gives smaller-area zones a higher `z-index` so nesting always renders correctly regardless of creation order. Zone membership (which nodes/zones are "in" which zone) is purely geometric — a node or zone's center point falling inside another zone's rectangle — there is no explicit parent/child link stored anywhere; see `getContainingZones()`.
- `state.mode` (`'select'`, `'connect'`, or `'zone'`, via `setInteractionMode()`) gates most canvas mousedown handling, but zone *drawing* (click-drag on empty canvas → a new rectangle, in the `canvasContainer` `mousedown` listener) fires in both `'zone'` mode and `'select'` mode — the dedicated Zone tool/button is kept as an explicit, discoverable way to do it, but a plain click-drag starting on genuinely empty canvas (same target check the `click` handler uses to clear selection: `canvasContainer`/`canvas-world`/`svg-layer`/`zones-container`) does it too, without switching modes. **A drag that creates a zone must set `suppressNextCanvasClick = true`.** The mouseup that ends the drag still fires a native `click` afterward on the same element (its target at mouseup time is empty canvas — the new zone's DOM element doesn't exist until the mouseup handler creates it), which would otherwise immediately clear the selection `createZone()` just made. This same suppression is needed by any other click-drag-on-canvas gesture added later, not just this one.
- Dragging a zone (`handleZoneDragStart`) moves its contents with it: at drag start it snapshots every node and every strictly-smaller nested zone whose center currently falls inside the dragged zone's rectangle, then applies the same mouse delta to all of them each tick. This is a one-time snapshot for the interaction, not a stored relationship — it doesn't contradict the "purely geometric, no parent/child link" rule above, since membership is still re-derived from scratch (via `isNodeContained`/center-point checks) the next time anything asks. Resizing a zone (`handleZoneResizeStart`) intentionally does *not* move contents — only dragging does.
- A hypervisor cluster's hosts and guest VMs are **not** separate stored entities — they're ordinary Physical Server (`server`) / Virtual Server (`vserver`) nodes dragged inside the cluster zone's rectangle, exactly like any other zone-membership relationship in this app. `getClusterHostNodes()`/`countClusterHosts()` find contained `server` nodes with the `isHypervisor` flag set; `getClusterGuestNodes()` finds every contained `vserver` node. `isHypervisor` is a flag on the node, not a `ROLE_TAGS` entry — it's mutually exclusive with Server Role (`updateNodeHypervisorFlag` clears `role` when set, and the inspector hides the Server Role picker while it's true), since a host's job is virtualization, not running an app role itself. Don't reintroduce a separate roster field on the zone for guests — it was tried (`zone.guestVMs`) and replaced because it duplicated data that already lives on real node objects and couldn't be dragged onto the canvas.
- Network- and security-category nodes (switch, vswitch, router, loadbalancer, firewall, …) carry two more manually-authored fields: `vlanIds` (trunk membership — which VLANs the device carries, toggled via `toggleNodeVlan`) and `accessRules` (an ordered list of `{id, action: 'allow'|'deny', protocol, source, destination, port, note}`, managed via `addAccessRule`/`updateAccessRule`/`moveAccessRule`/`deleteAccessRule`, using `state.ruleCounter` for ids). The inspector labels this list "Firewall Rules" for `security`-category nodes and "Access Control List (ACL)" for `network`-category ones — same data shape, different heading. Unlike the Firewall Rule Matrix below, these can't be derived from the topology (they're actual configured policy), so a typed list is the right model here — don't try to generate them from cabling/zones.
- A `user`-category node (a persona — DC Manager, Facilities Tech, a 3rd-party vendor support role, etc.) carries a `userType` key into `ACCESS_ROLES`. `checkUserAccessViolation()` flags it (red ring + warning badge on the card, and a warning block in its inspector) when it sits inside at least one zone but **none** of the zones containing it (`getContainingZones()` — every zone, purdue and cluster both) list that `userType` in their own `accessRoles` array. A user placed outside any zone isn't flagged — there's nothing to authorize against. A zone's `accessRoles` starts empty on creation (including every zone in the built-in seed designs, populated afterward by explicit `toggleZoneAccessRole()` calls — see `seedDemoLayout()`/`loadRecommendedDesign()`) — **this means an unconfigured zone authorizes nothing, so a freshly drawn zone will flag every user placed in it until its Access Roles are set**, which is expected, not a bug, but was reported once as "no matter where I place this user it says wrong zone" because the fix wasn't discoverable from the violation alone. The inspector's violation block now names the specific (smallest/most-specific, same tie-break as `findContainingSecurityZone()`) zone at fault and offers `authorizeUserZoneAccess()` as a one-click fix — grants that node's own `userType` on that zone directly, rather than making the user go find the zone, select it, and hunt its Access Roles checklist for the right entry. Keep offering that fix inline; don't regress to a bare warning with no path to resolving it.
- Persistence: `buildExportPayload()` is the single source of truth for what a saved/shared design contains. `loadTopologyState(incomingState)` is the single source of truth for rebuilding the live canvas from one — it's shared by file import (`importTopologyJSON`), the share-link loader (`loadFromShareLinkIfPresent`), and the autosave-restore path on boot (`bootApp`). Never reimplement the reset/rebuild sequence inline elsewhere.
- The Firewall Rule Matrix (`buildFirewallRuleMatrix()`) is a purely derived view — nothing about it is stored in `state` or persisted. It's recomputed from `state.connections` and `state.zones` every time the modal opens, via `findContainingSecurityZone()` (the same smallest-area-wins nesting rule used elsewhere) and the `PURDUE_OT_LEVELS`/`PURDUE_IT_LEVELS` boundary check. Keep it that way — don't cache or persist rule results, since they'd silently go stale the moment a node moves or a zone's level changes.
- Cable rendering has two modes, toggled by `state.cableRouting` (`'orthogonal'` default, or `'straight'`) via the toolbar's routing button — a view preference like `snapToGrid`/`zoom`, not persisted in `buildExportPayload()`. `renderConnections()` branches on it: straight mode draws an SVG `<line>`, orthogonal mode a right-angle `<path>` via `findBestRoute()`. Both endpoints are edge-anchored (`getNodeEdgePoint()`) rather than dead-center, on whichever side the primary axis points to — `horizontalFirst = Math.abs(dy) < NODE_COLLISION_H` (anything within one card-height of vertical separation counts as "same row" and exits sideways; anything past that exits top/bottom), since this app's diagrams are organized as horizontal Purdue-level bands, not by raw |dx| vs |dy|. The `#svg-layer` sits above `#nodes-container` (z-30 vs z-20) so a cable is never hidden behind an unrelated device — edge-anchoring is what keeps it from also overlapping its own endpoints' visible content once cables draw on top. **`getNodeEdgePoint()` and `getNodeCenter()` both compute the card's center from `NODE_HALF_W`/`NODE_COLLISION_H` (120px, matching the real rendered card height measured via Puppeteer).** They didn't always agree: `getNodeCenter()` used to have its own much shorter `NODE_HALF_H` (46px, implying a ~92px card) for zone-containment/access-violation checks, on the theory that changing it might shift those. It was actually just stale — undershooting the true card center by ~14px is small enough to rarely matter for routing direction (`dx`/`dy` differences between two nodes cancel a constant per-node offset out completely) but could occasionally misjudge zone containment for a node placed near a zone's edge. `NODE_HALF_H` is gone now; both functions use `NODE_COLLISION_H / 2`. Don't reintroduce a separate, looser center for either.
- Orthogonal routing is a single tier: every call to `renderConnections()` — live drag included — uses the same real A* pathfinder, `findBestRoute()`. `findGridPath()` runs A* over a grid (`GRID_CELL_BASE` = 24px, matching the snap-to-grid pitch) spanning the two endpoints plus a margin, with a per-move turn penalty (`GRID_TURN_PENALTY`, biasing toward long straight runs over a staircase) and hard, *direction-specific* zone-border avoidance — `hBlockGrid` forbids horizontal moves near a zone's top/bottom edge, `vBlockGrid` forbids vertical moves near its left/right edge, so a normal perpendicular *crossing* (which most inter-level cables do repeatedly) is never restricted, only running parallel-and-close to a border is. `findBestRoute()` wraps it: `simplifyOrthogonalPath()` collapses the grid search's cell-by-cell points into long straight segments, `pathMidpoint()` finds the badge/VLAN-chip anchor at a given fraction (default half) of the path's *arc length* (not just the middle point in the array, since segments vary in length) plus a perpendicular unit vector. That default-half anchor is cosmetic, not load-bearing like the route itself, and `pathMidpoint()` has no idea zones exist — so `findBadgeAnchor()` wraps it: if the plain midpoint lands on a zone's floating label chip (same problem `labelPenaltyGrid` solves for the route, but this is a separate check since the badge isn't part of the A* search), it retries a few other fractions along the *same* path before falling back to the true midpoint anyway. Was needed in practice, not just in theory — a multi-VLAN trunk's chip *stack* (each membership offset `10 + i*9` px out from the anchor, so the reach adds up fast) landing on a cluster zone's name was reported as part of "the routing looks messy."
- **Every route is forced to travel straight out from each pin, in that pin's own exit direction, for a short distance before the router is allowed to bend it** — `findBestRoute()`'s `PIN_STUB_LENGTHS`/`findPinStub()`. Without this, A* is completely free to bend on its very first grid step, and since it's optimizing total cost (not "reads as a deliberate lead-out"), it very often did: measured on the reference design, 19 of 34 connections' first *rendered* segment ran in the wrong axis entirely for the pin it left (e.g. a bottom-exit pin's first visible move was sideways, not down), reported by a user as "a connection on the left... going straight up rather than out for a short run then curving up." Root cause: the search's own real first move (in the correct direction) collapsed to near-zero length and vanished in `simplifyOrthogonalPath()`, leaving the next, perpendicular segment looking like the start. The fix searches from a point already stubbed out in the mandated direction rather than from the raw pin — `PIN_STUB_LENGTHS = [36, 24, 12]`, tried longest first, since this app's seeded layouts often pack same-row cards only ~30px apart and a single fixed length either overshoots into the neighbor constantly or has to be too short to read as a stub anywhere. **Getting the pin itself spliced back onto the front/back of the resulting path without introducing a diagonal sliver is the fiddly part** — the grid search snaps x and y independently, so even a stub that only moved one axis can leave the *other* axis drifted by up to half a cell once snapped; the code walks the *entire* leading/trailing run of points sharing that drifted value (not just the first/last point) and pins all of them back to the exact pin coordinate, bounded so the two runs can never cross. Do not simplify this to "just fix `gridPoints[0]`" — that was tried, and it works right up until the search's first several points continue straight before its first real turn, at which point only correcting the very first one just moves the diagonal sliver one point further in.
- **`simplifyOrthogonalPath()` runs its dedupe-then-merge pass up to three times, not once** (`simplifyOrthogonalPathPass()` is the single-pass version it loops). One pass can leave a fresh problem behind: dropping a "fake corner" whose surrounding segments turn out collinear can leave the points on either side of it newly adjacent *and identical* — the same zero-length step the pass's own dedupe step already handles, just produced too late in that same pass to catch. This showed up for real, not hypothetically: the pin-stub splice above occasionally produced exactly this (a short "there and back" detour collapsing to nothing), which without the repeat left an invalid `<path>` (`Q` command with a `NaN` control point, since `buildRouteRuns()` divides by a distance that came out zero). If you ever see that error in the console, look for a source of duplicate-after-merge points before adding another one-off fix — the repeated-pass approach handles the general case.
- **There used to be a second, cheaper tier** — `findClearRoute()`/`buildRouteAt()` (a single-bend elbow tried at a handful of candidate positions), used for `renderConnections(true)` during a node/zone drag's own `onMove` so A*'s per-connection cost wouldn't add up over many mousemove ticks. It was removed as the direct fix for a real, reported problem: `findClearRoute()` and `findBestRoute()` can legitimately produce different-looking paths for the same two points (they're different algorithms with different notions of "clear"), so a route that looked fine while live-dragging could visibly jump to something more convoluted the instant the mouse was released and the real router took over — reported as "the routing looks ok, then I release... and it changes, usually for the worse," for both a single node drag and a zone-group drag. Measured full A* at ~15ms for this app's whole 34-connection reference design — well inside a frame budget on its own — so the fix wasn't a faster router, it was **`throttledRenderConnections()`**: still the one real A* router during a drag, just capped to run at most every `CONNECTIONS_RENDER_THROTTLE_MS` (50ms) while the mouse keeps moving, with a trailing call so the final in-drag position still gets rendered even if the mouse pauses mid-interval. The dragged node/zone's own on-screen position (a plain `style.left`/`style.top` write) is never throttled, only the comparatively expensive re-route. Every drag's `onUp` calls `cancelThrottledRenderConnections()` before its own final, unthrottled `renderConnections()`, so a stray trailing timer from just before mouseup can't fire a redundant extra render after the drag has already settled. **`findClearRoute()` is still there and still used** — now only as `findBestRoute()`'s own last-resort fallback for the rare connection A* finds no path for at all (see `relaxedObstacles` above). Don't reintroduce a second "cheap but different" live-preview router for performance reasons without also solving the visual-mismatch problem that got this one removed — a throttled real router beats a fast approximate one for anything the user is meant to trust the look of.
- `findGridPath()`'s obstacles come from `buildRouteObstacles()`: every other node as a rect, plus every hypervisor cluster zone neither endpoint sits in as **one** big rect (routing around a whole cluster, not dodging each VM inside it individually — cheaper and produces a cleaner path). It also adds a small inset-interior-only rect (`OWN_NODE_INTERIOR_INSET`, 20px in) for the connection's *own* two endpoint nodes — without it, nothing stopped a route from leaving a card's edge and immediately cutting back across that same card's interior on the way past it (p1/p2 sit right on the true edge, so the full card can't be a plain obstacle, but the deeper interior can). **This inset addition is a refinement, not a correctness requirement — pass `includeOwnNodeInterior: false` (the `buildRouteObstacles()` 5th arg) to get the old, unrefined obstacle set, and `findBestRoute()`'s `relaxedObstacles` param retries with that set if the strict one finds no path at all.** In one tight corridor next to a large cluster zone, the strict set boxed the search in completely (no path at any margin) where the relaxed set still found one — always keep that retry rather than letting A* fail straight through to the crude fallback router, which ignores obstacles (including cluster zones) entirely. Obstacle/border-avoidance costs are precomputed once per connection into `Uint8Array` grids (`blockedGrid`, `hBlockGrid`, `vBlockGrid`) rather than tested against every obstacle on every cell the search visits — that lazy version was the dominant cost by roughly 20x. If the search fails at the base margin (usually because what it needs to route around — e.g. a cluster spanning most of a level — is wider than the search area), `findGridPath()` retries at each wider margin in `GRID_SEARCH_MARGINS` before giving up. **Keep the border-avoidance band to a single grid line per edge (`avoidCells = 0` in `findGridPathInRegion()`) — do not widen it, and do not add a second hard-blocked row/column anywhere near a border for any reason.** A multi-cell band was tried and broke pathfinding outright: this app's Purdue zones are frequently only ~50px apart, and two adjacent zones' avoidance bands (each already ≥24px at this grid resolution) merged across that gap and walled it off completely, making the far side unreachable no matter how large the search margin got. This bit again in miniature: a zone's name/stat chip floats just above its top edge (`renderZoneElement()`'s `-top-3` handle), and a route hugging that top border the way it's allowed to hug the other three could cut through the chip's text — the first fix hard-blocked one extra row there, which read fine until it sealed off the only route through a different tight corridor elsewhere in the same reference design (verify against the full 34-connection design, not just the one case you're fixing). The actual fix is `labelPenaltyGrid`: a *soft* per-cell cost on horizontal moves in that row (same `SIBLING_AVOID_PENALTY`-style mechanism as sibling-avoidance below), which still avoids the chip whenever a reasonable detour exists without ever making a route flatly impossible. If a wider hard-blocked band is ever needed for something else, it has to come from a finer grid (smaller `GRID_CELL_BASE`) in the affected region, not from a larger `avoidCells` — and any new border-adjacent restriction should default to a soft cost, not a hard block, unless you can prove it can never seal a corridor.
- This is still a bounded local search, not global optimization — it doesn't try to keep separate cables from crossing *each other* (there's no shared "which cells has another cable already claimed" cost), and a genuinely walled-in endpoint (no clear cell adjacent to it at any tried margin, even after the `relaxedObstacles` retry above) falls through to `findClearRoute()` as a last resort rather than failing outright. Verified on the 60-node/34-connection reference design (re-check with a real browser + Puppeteer, not jsdom — see Testing below): zero node collisions (a cable never cuts through any node's interior, including its own endpoints' cards), zero border-hugging, all A*-produced segments axis-aligned, ~0.2ms of routing math per connection (precomputed grids), ~15ms for a full re-route pass of every connection (this is now also the per-tick cost during a throttled drag, not just the settled render — see the routing-tiers note above).
- Rendering is a separate cosmetic pass over the router's plain sharp-cornered `points` (never the other way around — routing math always stays on the simple straight-segment shape). `renderConnections()` computes every connection's route first (phase 1), *then* finds where different cables' routes cross (phase 2, high-quality pass only), *then* renders (phase 3) — crossing detection needs every cable's full route up front, so it can't happen inline per-connection like the rest of the pipeline. `buildDecoratedPathD()` produces the actual `<path d>`: `buildRouteRuns()` trims each straight run back by `ROUTE_CORNER_RADIUS` at both ends (less, for a short run, so two curves on a short run can't overlap) and a quadratic curve bridges each trimmed pair using the original sharp corner as the control point — a cheap way to get a rounded "flowing" bend without arc-flag math. `findCableCrossingHops()` finds every *perpendicular* intersection between two different cables' straight segments (`perpendicularCrossing()` — parallel/collinear overlap is a different problem, mitigated separately below, not by a hop) and assigns each crossing to the later of the two cables (arbitrary but deterministic) to draw as a small loop, the classic schematic "jumps over, not connected here" symbol — `runPathFragment()` splices a `Q`-curve bulge into whichever run the crossing falls on, always bulging the same fixed direction (up for a horizontal run, right for a vertical one) rather than one relative to travel direction, so a cable's own loops all read consistently. **Crossings must be deduplicated** (`addHop()`'s ~22px proximity check, one hop-width-plus-margin, not just "the same point") — several sibling cables sharing a pin (see below) commonly funnel through the same detour and cross each other at, or within a couple dozen px of, the same physical point several times over (once per pair), and without merging those nearby-but-distinct crossings into one loop it draws several loops back to back with no straight lead-in between them, reading as a cramped "wavy" tangle rather than distinct crossings. `nearAnyEndpoint()` (which skips drawing a hop right where a cable leaves a device, since that's a real junction, not an incidental crossing) compares against each route's **actual first/last drawn points** (`entry.points[0]`/`points[...length-1]`), not its ideal `p1`/`p2` anchor — the A* grid snaps the real path onto grid cells, so the drawn start can land several px from the anchor, and comparing against the anchor let a crossing sitting exactly on a sibling's real starting point slip through undetected. A loop is silently skipped (falls back to a plain straight pass-through) if it's too close to the run's own end — e.g. a crossing that happens to land within a rounded-corner's curve zone rather than a run's straight span; rare, and a missed loop just reads as an ordinary crossing rather than a visible glitch, so it's a fine place to give up. Endpoint connection-point dots (small filled circles at both `p1`/`p2`) exist specifically so a cable's actual attachment point is never ambiguous next to a crossing loop or another cable running close by.
- Every card has exactly one connection point ("pin") per side — its exact center, always, regardless of how many cables share that side — deliberately mirroring a schematic symbol's fixed leads (a resistor's pin doesn't move depending on what else is on the board). `getNodeEdgePoint()` no longer takes a lane-offset parameter; there used to be one (`computeLaneOffsets()`, fanning a side's cables out across it, sorted by angle) specifically so multiple cables sharing a side wouldn't start from the exact same pixel and overlap for however long they happened to travel the same way — but that made a cable's own attach point shift depending on what else was wired to that side, which a real user flagged as reading as "a mess" and explicitly asked to fix by making it PCB-pin-like. Don't reintroduce per-side fan-out at the pin; if cables sharing a pin need to visually separate, that has to happen in the *routing* (the mitigation below), not by moving where they attach.
- Mitigation for parallel/overlapping cables — genuinely separate cables whose routes run right on top of each other, which reads far worse than a crossing since there's no single point to put a hop at, and matters more now that sibling cables start from the exact same pixel (see the fixed-pin note above) rather than being pre-separated. `collectSiblingSegments()` gathers every segment of every *already-routed* connection sharing an endpoint with the current one, and `findGridPathInRegion()` applies `SIBLING_AVOID_PENALTY` as a soft per-cell A* cost (`siblingPenaltyGrid`, same precomputed-once-per-search pattern as the obstacle/border grids) so a later sibling prefers a different way through when one isn't much longer — soft, not a hard block, since through a genuine bottleneck (the only realistic path) reusing it anyway is correct, not a bug. This only works one direction: connection *N* only ever avoids connections *before* it in `state.connections`, never after — order is what breaks the tie, and it's arbitrary but stable. This doesn't get cables to zero long-overlap pairs: several groups (e.g. everything fanning out from one facility supervisory server to its field devices) still share a real bottleneck corridor for a genuine stretch, same as a real cable tray would. If that residual still reads as unclear, the fix is *not* a bigger penalty (tested — a much stronger one barely moved the needle once past the easy cases, since the remaining ones really are bottlenecks); it would need actual differentiation along the shared stretch, e.g. a small perpendicular offset applied to the rendered curve itself for cables detected as parallel-overlapping, independent of the routing math.

## Deployment

GitHub Pages serves this repo directly from the `main` branch root — pushing to `main` auto-redeploys within about a minute. There is no CI, no `.github/workflows`, and no separate `gh-pages` branch. **Do not** introduce a build step or move source into a `src/` or `dist/` folder without also updating the Pages source setting, or the live site will break.

## Making changes

Because everything is one file, most changes touch multiple spots that must stay in sync:

1. **Adding a new draggable component type** requires edits in two places:
   - A new entry in `COMPONENT_METADATA` (name, category, `icon` SVG string sized `w-5 h-5`, `color` border classes, `powerKW`, `defaultPorts`, `specs`).
   - A matching palette card `<div draggable ondragstart="handlePaletteDragStart(event, '<key>')">` in the left sidebar, under the appropriate category section, with its own `w-4 h-4` icon and a distinct Tailwind color swatch (`bg-*-950/60 border-*-500/30 text-*-400`) so it doesn't blend in with neighboring cards in the same category.
   - The palette item count badge updates itself automatically from `Object.keys(COMPONENT_METADATA).length` — no manual count to edit.
   - Give `defaultPorts` a non-zero value even for abstract nodes (e.g. cloud/remote-site) — the ports label uses `meta.defaultPorts || 24`, so a literal `0` falls back to displaying `24`.

2. **Never interpolate user-editable or imported data directly into `innerHTML`.** Node labels, IPs, notes, zone labels, and peer/cable labels are all user-controlled (either typed directly, or loaded from an imported JSON file) and must be passed through the `escapeHtml()` helper before being placed in a template string. This app takes arbitrary `.json` files via the "Load" button — treat every field from an imported file as untrusted.

3. **Re-rendering an existing DOM node or zone must remove the old element first.** Both `renderNodeElement()` and `renderZoneElement()` do `document.getElementById(id)?.remove()` before creating the replacement. If you add another code path that re-renders an existing entity by id, follow the same pattern — skipping it silently leaves a stale duplicate element (with its own event listeners) behind, which is exactly the bug that was fixed in this codebase once already.

4. **`importTopologyJSON()` must stay defensive.** It accepts arbitrary files from the "Load" button. Keep validating `archetypeKey` against `COMPONENT_METADATA` before calling `createNode`, and keep resetting `nodesContainer`, `cableGroup`, and `zonesContainer` (plus `state.nodes`/`connections`/`zones`) before rebuilding, so a partially-invalid file can't leave the canvas in a mixed old/new state.

5. **Keep `buildExportPayload()` and `loadTopologyState()` in sync** with whatever top-level state fields exist (`nodes`, `connections`, `zones`, `vlans`, `counter`, `zoneCounter`, `cableCounter`, …) — if you add a new piece of persistent state, include it in both functions, and bump the `version` string in `buildExportPayload()` if the schema changes in an incompatible way. These two functions back JSON export/import, the shareable-link feature, and autosave alike — fixing one without the other silently breaks the other two.

6. **Call `scheduleAutosave()` at the end of every function that mutates `state`** (creating/deleting/editing a node, connection, zone, or VLAN; drag-end for nodes and zones). It's cheap and debounced (350ms), so prefer calling it defensively over trying to reason about whether a given mutation "really" needs persisting. It writes through `buildExportPayload()`, so a new state field only needs to be added there, not to every autosave call site.

7. **IDs must not collide within a session.** Nodes, zones, cables, and access rules each use their own counter (`state.counter`, `state.zoneCounter`, `state.cableCounter`, `state.ruleCounter`) rather than `Date.now()` — several can be created in the same synchronous tick (e.g. the seed demo, or a bulk import), and millisecond timestamps are not guaranteed unique across rapid calls. Follow the same counter pattern for any new entity type.

8. **Call `refreshZoneDerivedState()` after anything that could change zone membership or a zone's access rules.** It re-renders every cluster zone's host/guest-count badge and every `user`-category node's access-violation styling, since both are computed live at render time from current node positions and `zone.accessRoles`/`node.isHypervisor` — they are not stored, so a stale render is the only way they'd ever be wrong. Existing call sites: node create/delete, node drag-end, `updateNodeRole`, `updateNodeHypervisorFlag`, `updateNodeUserType`, zone drag/resize-end, `toggleZoneAccessRole`, `updateZoneType`, `executeDeleteZone`, and the end of `loadTopologyState`. Add it to any new mutation in the same family (e.g. a future bulk-move or duplicate feature).

## Testing

There is no automated test suite. Verify changes by actually opening the page in a browser:

```bash
python3 -m http.server 8000   # then visit http://localhost:8000/index.html
```

At minimum, after any change, check the browser console for errors and exercise the golden path: drag a device onto the canvas, cable two devices together, draw a zone, select/edit each of node/cable/zone in the inspector, and run a Save → Load round trip. `node -e "new Function(...)"` on the extracted inline `<script>` contents is a fast way to catch syntax errors before opening a browser.

For anything involving real rendered layout — cable routing/edge-anchoring especially — a headless real browser (`puppeteer-core` driving `google-chrome-stable`, if available in the environment) is far more trustworthy than jsdom: jsdom doesn't compute real CSS layout, so `getBoundingClientRect()` returns zeros and any check built on it is checking nothing. Confirmed this the hard way mid-session: a card-height constant that looked right in jsdom-verified logic was actually ~28px off the real rendered size. Puppeteer also lets you pull `state.connections` and each cable's live `<path d>` via `page.evaluate()` and parse the actual segment points — much more precise than eyeballing a screenshot for things like "is there a suspiciously short segment here" (a good general smell test: flag any straight `L`-to-`L` run under ~6px, or any route segment that intersects a node rect it's not attached to — both catch real routing bugs a screenshot alone won't). Screenshots are still essential for anything about visual *quality* (crampedness, overlap, legibility) that a pure data check can't judge — take both.

## Conventions worth preserving

- Tailwind utility classes are used inline everywhere; there's no separate CSS file to touch aside from the `<style>` block in `<head>`.
- SVG icons are hand-written inline (24×24 viewBox, `fill="none" stroke="currentColor"`), not pulled from an icon library — keep new icons in the same style for visual consistency.
- Toasts (`showToast`) and the custom confirm modal (`showConfirmModal`) exist specifically to avoid native `alert()`/`confirm()`, which block the extension/automation-driven browsing this app is sometimes tested with. Keep using them for any new user-facing notifications or destructive-action confirmations.
